# Keep the Lambda warm during business hours

A scheduled EventBridge rule pings the Lambda every 5 minutes on weekdays, roughly
08:00–20:00 ICT, with a `{"warmup": true}` event. The handler treats that event as a
prime-and-return: it loads the SSM secrets and builds the Bolt app (the cold-start
work), then returns without entering the Slack request path. We do **not** move to an
always-on host or provisioned concurrency.

This **refines** ADR-0002 (Lambda + HTTP mode); it does not reverse it. The bot stays
serverless and pay-per-usage.

## Why

`/dayoff` opens a modal, so it must run synchronously (the `trigger_id` is valid for
only ~3s, and lazy listeners self-invoke too late to use it). Under `faas=True` the app
runs with `process_before_response=True`, which means the HTTP ack is not flushed when
`ack()` is called — it is flushed only when the handler returns, **after** the
`views_open` round-trip. On a cold start the chain `import + SSM + build_app +
get_employee + remaining_balances + views_open` occasionally exceeds 3s. The modal still
opens (the trigger outlives the late ack by a hair), but Slack shows
`operation_timeout` to the user. Warm, the same chain is well under 1s.

The message is generated by Slack, not by us — there is no app-side way to suppress or
restyle it. The only cure is to ack within 3s, which on a cold start means not being
cold. Keeping the container primed during the hours the team actually uses `/dayoff`
removes the message where it matters.

Business-hours-only is deliberate: nights and weekends the function still scales fully
to zero, so the pay-per-usage model that drove ADR-0001/0002 holds. The pings are a
handful of thousand tiny invocations a month — far inside Lambda's perpetual free tier —
so the cost is $0.

## Shape

- `lambda_handler.handler`: after priming secrets + app (the existing first-invocation
  bootstrap), `if event.get("warmup"): return {"ok": True}` — short-circuits before the
  Slack request path, which expects a signed HTTP event.
- Terraform: an `aws_cloudwatch_event_rule` (`cron(0/5 1-12 ? * MON-FRI *)`, UTC ≈
  08:00–20:00 ICT), an `aws_cloudwatch_event_target` whose `input` is
  `{"warmup": true}`, and an `aws_lambda_permission` letting EventBridge invoke the
  function. Edit the cron to change the window.

## Considered alternatives

- **Do nothing (pure scale-to-zero).** Also $0 and architecturally cleanest, but eats
  the occasional cold-start `operation_timeout`. The message is the price of a container
  that truly dies when idle.
- **Hide / restyle the message.** Not possible — it is Slack-side, triggered solely by
  missing the 3s ack.
- **Reorder `ack()` earlier / lazy-listen the modal.** No effect under
  `process_before_response` (the ack flushes after the handler), and lazy listeners
  can't open modals reliably (the `trigger_id` expires across the self-invocation).
- **Always-on host keeping Socket Mode** (the option ADR-0002 already weighed). Removes
  the message completely and needs ~no code change, but ~$3–9/month idle — it reverses
  the pay-per-usage rationale.
- **Provisioned concurrency.** Guaranteed warm, but ongoing $ for idle capacity.
- **SnapStart (Python).** Snapshots the init phase so cold starts are fast and it covers
  concurrent cold starts too — but needs a published version + alias + a Function-URL
  repoint, and our secrets are fetched at runtime (post-restore), so the win is partial
  without an `afterRestore` hook. More moving parts than the problem warrants today.

## Consequences

- During business hours the container is **behaviourally** always-on (kept alive on
  purpose), so it is not *truly* scale-to-zero then — but the cost is still $0. Only
  off-hours is it genuinely idle/zero.
- An off-hours cold start can still flash `operation_timeout`. Accepted: almost nobody
  files leave at 2am, and the modal works regardless.
- A *simultaneous* second `/dayoff` in the same cold instant can still hit a cold
  container (keep-warm holds one warm). Rare at this team size; SnapStart or provisioned
  concurrency is the lever if that ever matters.
- The execution role already allows the function to be invoked; the new permission only
  adds the EventBridge principal for this rule.
