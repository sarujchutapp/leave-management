# Cold-start mitigation for the leave bot

How we keep `/dayoff` from showing Slack's `operation_timeout` message, why the fix is
consistent with our cost philosophy, and exactly where it stops working. Companion to
[ADR-0007](../docs/adr/0007-keep-warm-ping.md) (the decision record) — this is the fuller
reasoning and the honest limits.

## The symptom

A user runs `/dayoff`. The modal opens normally — but Slack *also* flashes
`/dayoff failed with the error "operation_timeout"`. It's intermittent, and it tracks
with the bot having been idle for a while.

The message is **generated by Slack, not by us.** There is no app-side toggle to hide or
restyle it. Slack shows it whenever our endpoint fails to return the ack (an HTTP 200)
within **3 seconds** — and a late ack can't take it back. So "hide the message" was never
an option; the only cure is to ack in time.

## Root cause

Three facts combine:

1. **`/dayoff` must be synchronous.** It opens a modal, which needs the `trigger_id`, and
   that token is valid for only ~3s. Bolt "lazy listeners" run as a *separate* Lambda
   invocation that arrives too late to use the trigger reliably — so the modal open can't
   be deferred.
2. **On Lambda we run `process_before_response=True`** (required — the container freezes
   after the handler returns, so there's no background thread to finish post-ack work).
   The consequence that bites us: **the HTTP ack is not flushed when `ack()` is called —
   it's flushed when the handler *returns*,** i.e. *after* the `views_open` round-trip.
3. **Cold start.** The first request to an idle/new execution environment pays for
   `import (slack_bolt + boto3) → load secrets from SSM → build_app → get_employee →
   remaining_balances → views_open`, all before that flush.

Warm, that chain is well under 1s. Cold, it occasionally crosses 3s. The modal still
appears (the trigger outlives the late ack by a hair), but the ack is late → Slack
complains. So it's a **cosmetic** failure on cold starts, not a functional one.

Why we can't just reorder: moving `ack()` earlier does nothing under
`process_before_response` (the flush waits for the handler to return regardless). Bumping
memory helped (512 MB → 1024 MB closed most of the gap — see the comment on the Lambda
resource) but didn't eliminate it.

## Revisiting the philosophy first

Before throwing infrastructure at it, we pinned down what "pay-per-usage / scale to zero"
actually means for us, because it decides which fixes are allowed:

- **[ADR-0001](../docs/adr/0001-dynamodb-for-persistence.md): DynamoDB on-demand,
  pay-per-query.** This is the layer whose cost *grows with real usage*. It is the heart
  of the model — the thing that genuinely costs nothing when nobody uses the bot, and the
  differentiator vs. always-on HR tools that bill for idle capacity.
- **[ADR-0002](../docs/adr/0002-aws-lambda-http-mode.md): Lambda + HTTP mode.** This
  *extended* the idea to compute. But read its real rationale: it rejected an always-on
  host because that **"costs ~$3–9/month even while idle."** The concern was **paying for
  idle**, not idleness as a virtue. "Scale to zero" was the *means*; "no idle cost" was
  the *end*.

That distinction is the whole game. A fix that (a) leaves DynamoDB pay-per-query
untouched and (b) costs $0 at idle is *consistent with the philosophy*, even if the
compute layer no longer literally hits zero invocations.

## The solution: a keep-warm ping

An EventBridge rule invokes the Lambda every **4 minutes** with `{"warmup": true}`. In
`lambda_handler.handler`, that event is a **prime-and-return**:

```
load secrets (once) → build app (once) → if event.get("warmup"): return {"ok": True}
```

It primes the container (secrets fetched, Bolt app built) and returns **before** the Slack
request path. So when a real `/dayoff` arrives, the heavy work is already done and the ack
lands in well under a second.

Why this is consistent with the philosophy:

- **The ping never queries DynamoDB.** It short-circuits before any handler runs — no
  `get_employee`, no reads/writes. The pay-per-query layer (ADR-0001) is *completely
  untouched*; it still charges exactly per real query.
- **Idle cost is $0.** Every 4 minutes ≈ **10,800 invocations/month**, each a ~100ms
  prime-or-no-op at 1 GB ≈ ~1,080 GB-s/month. Lambda's *perpetual* free tier is 1,000,000
  requests + 400,000 GB-s/month — so we use ~1% of one limit and ~0.3% of the other.
  EventBridge scheduled invocations are free at this volume. The bill is **$0**, so
  ADR-0002's "don't pay for idle" end is satisfied — by a different route than literal
  scale-to-zero.

Why **4 minutes** and not 5: AWS does not publish a guaranteed keep-alive; idle
environments are reclaimed somewhere in a fuzzy **~several-to-tens-of-minutes** window,
and there are reports of reclaim as early as ~5–6 min. 4 minutes buys margin under that
lower bound at no extra meaningful cost.

Why around the clock and not business-hours-only: a business-hours window would preserve
literal compute idleness at night — a purity that costs nothing, shows users nothing, and
still leaks an off-hours cold-start message. Since the DB is untouched and idle cost is $0
either way, 24/7 is strictly better for the user.

## Alternatives considered (and why not)

| Option | Verdict |
|---|---|
| **Do nothing** (pure scale-to-zero) | Also $0 and cleanest; but eats the occasional cold-start message. The message is the price of a container that truly dies when idle. |
| **Hide / restyle the message** | Impossible — it's Slack-side, triggered purely by missing the 3s ack. |
| **Reorder `ack()` / lazy-listen the modal** | No effect under `process_before_response`; lazy listeners can't open modals reliably (trigger expiry). |
| **Business-hours-only ping** | Preserves off-hours compute idleness that costs nothing and helps no user, while still leaking an off-hours message. Rejected for plain 24/7. |
| **Always-on host (Socket Mode)** | Removes the message, ~no code change — but ~$3–9/mo idle, i.e. pays for idle, the thing ADR-0002 set out to avoid. |
| **Provisioned concurrency** | Guaranteed warm, but ongoing $ for idle capacity. |
| **SnapStart (Python)** | Snapshots init; fast cold starts incl. concurrent ones. But needs a published version + alias + Function-URL repoint, and our secrets load at runtime (post-restore), so the win is partial without an `afterRestore` hook. More moving parts than the problem warrants today. |

## Limits — where this stops working

The ping makes the message **rare**, not **impossible**. Honest residual cases:

1. **AWS recycles environments regardless of recent use.** Even a freshly-pinged
   environment gets retired periodically (routine aging, deploys, capacity rebalancing).
   The invocation right after a retirement is cold — so a cold start can still slip
   through occasionally.
2. **One ping keeps *one* environment warm.** Two `/dayoff`s in the same cold instant →
   the second spins up a new, cold environment. Rare at our team size, but real.
3. **The lower bound is fuzzy.** 4 minutes is margin, not a guarantee; AWS could in
   principle reclaim faster under pressure.

In all three, the failure is the same **cosmetic** message — the modal still opens and
nothing breaks. So we've traded "sometimes" for "rarely, on an edge case."

## When to escalate

Only if the residual cases start mattering:

- **Concurrent cold starts become common** (team grows, bursty usage) → **SnapStart**
  (free-ish, covers concurrency) or **provisioned concurrency** (paid, guaranteed).
- **A hard "never cold" guarantee is required** → provisioned concurrency.

Until then, the ping is the right amount of effort: $0, no DB impact, no Slack-side
change, and it keeps the pay-per-usage story honest where it counts.
